## 0. 唯一依据与优先级

1. 《828C功能治具说明(1).pdf》：治具接口、串口参数、`(RD_NUM)`、`(START,x)`、JSON 返回格式及一条有效请求对应一条有效响应。
2. 《828C功能治具说明例子.xlsx》Sheet1：用户项目中的具体转换示例、双串口角色、末尾回车换行、**启动后 3 秒未收到测试主板数据返回 ERR**；普通项目 `D1-1` 的输出实例。

## 1. 项目目标与范围

实现：PC 上位机 ⇄ UART2 ⇄ STC12C5A60S2 协议转换板 ⇄ UART1 ⇄ 原测试主板。
- UART2：接收 828C 命令，返回 828C JSON。默认 115200、8 数据位、1 停止位、无校验。
- UART1：向原主板发送 `test1\r\n` 等命令，接收原测试行。**UART1 波特率在现有资料中未规定，必须配置，不得默认其必然为 115200。**
- 原测试主板无需修改固件。
- 使用 Keil C51，生成 `.uvproj`/`.uvprojx`（环境允许时）或至少输出完整 C51 源码、添加文件说明和清晰的 Keil 构建步骤。
- 不实现 PC 上位机、不更改原测试主板协议、不设计新上位机上传格式。

## 2. 硬件接口约束

828C PDF 20Pin 牛角定义：1=PASS（输出，低有效）；2=FAIL（输出，低有效）；3=START（输入，低有效）；4=GND；8=RX（主板 TTL 通讯）；9=TX（主板 TTL 通讯）；10=GND；11/12/13/14=模号 1/2/3/4 输入（低有效）；17/18=24V；19/20=GND；其他按 PDF 空脚。**20Pin 是治具侧定义，不表示将 24V 接到 MCU IO。**

建议 MCU 串口映射（必须核对该芯片引脚表、封装和现有板原理图）：UART1 `P3.0/RXD`、`P3.1/TXD`；UART2 `P1.2/RXD2`、`P1.3/TXD2`。TX 接对端 RX、RX 接对端 TX，地线共参考；PC 若为 USB 接口，使用适合的 USB-TTL 转换器并核对 3.3V/5V 电平。PASS、FAIL、START、模号及其电路接法不能仅凭这份需求擅定 GPIO 或电路。

## 3. 严格外部接口协议

### 3.1 串口设置和终止符

- UART2 上位机：115200、8N1。
- PDF 要求完整返回数据帧末尾有换行回车；Excel 明确提出**所有指令加回车换行**。工程统一使用 `\r\n`（字节 `0D 0A`）作为**发送**结束符；接收侧做完整命令帧识别，可在完整帧后剔除 `\r\n`。若实机上位机发送无终止符的 `(RD_NUM)`/`(START,x)`，以完整右括号 `)` 结束也可识别，但不得将半帧误识别成命令。该兼容行为应单测。
- 所有 JSON 使用 ASCII 双引号，输出无多余文字、日志或多帧报告，最后追加 `\r\n`。

### 3.2 模号识别

| UART2 接收 | 条件 | UART2 返回（附 `\r\n`） |
|---|---|---|
| `(RD_NUM)` | 仅检测到模号 1 | `{"Result":"1"}` |
| `(RD_NUM)` | 仅检测到模号 2/3/4 | 分别 `{"Result":"2"}` / `{"Result":"3"}` / `{"Result":"4"}` |
| `(RD_NUM)` | 无可识别模号 | `{"Result":"ERR"}` |

模号由 20Pin 第 11–14 引脚低电平状态确定，不得取上位机指令中的 `x` 冒充实际模号。多个模号同时有效时，PDF 未说明；不得武断选其中一个，暂返回 ERR 并在待确认事项记录。

### 3.3 启动测试

| UART2 接收 | 前提 | UART1 发送 |
|---|---|---|
| `(START,1)` | 物理模号为 1 | `test1\r\n` |
| `(START,2)` | 物理模号为 2 | `test2\r\n` |
| `(START,3)` | 物理模号为 3 | `test3\r\n` |
| `(START,4)` | 物理模号为 4 | `test4\r\n` |
| `(START,x)` | 指令模号与实际模号不一致 | UART1 不发送；UART2 返回 `{"Result":"ERR"}\r\n` |

上述 `test1`、`test2` 由 Excel 第 3 行明确示范，`test3`、`test4` 为同一指令映射模式的实施假设；请为 3/4 增加独立校验用例并在实机核对。指令符合要求时，不能先发“启动成功”占用本次请求的唯一正式响应；须在测试完成后返回整帧结果或超时 ERR。

### 3.4 返回 JSON（严格保留 PDF/Excel 示例）

PDF 给出的有效示例：

```json
{"MH":"1","Result":"OK","OPEN":":OK"}
{"MH":"1","Result":"NG","OPEN":"1-2:NG"}
{"MH":"1","Result":"NG","OPEN":":OK","PN":"9999mV:NG"}
{"MH":"1","Result":"OK","OPEN":":OK","PN":"534mV:OK"}
```

Excel 给出的有效示例：

```json
{"MH":"1","Result":"OK","OPEN":"OK"}
{"MH":"1","Result":"NG","OPEN":"1-2:NG"}
{"MH":"1","Result":"NG","OPEN":"OK","PN":"9999mV:NG"}
{"MH":"1","Result":"OK","OPEN":"OK","PN":"534mV:OK"}
```

Excel Sheet1 第 19 行具体转换必须实现：

```text
UART2 收到：(START,1)\r\n
UART1 发出：test1\r\n
UART1 收到：D1-1,9.0,6.0,V,(2-5=12.6),NG\r\n
UART2 最终整帧（若本轮只有这一测试项）：
{"MH":"1","Result":"NG","D1-1":"NG"}\r\n
```

对于普通项目的上限、下限、单位、实测值：解析可用于校验和记录，**不能擅自追加到 `D1-1` 的上报值**；示例规定该字段值为 `NG`。同类项目按 Excel 的“其余以此类推”处理。OPEN/PN 必须支持明确示例格式，不得以普通项目逻辑覆盖其特殊数据格式。JSON 主字段必须写 `MH`、`Result`；不要拼写为小写或替换成自定义字段。

## 4. 原测试主板输入样本及解析

`数据新格式(2).txt` 的顺序及样本包括：

```text
test
Open,10.0,0.0, ohm,(8-78=978.4,9-84=992.2,...),NG
Short,99.9,2.0,Mohm,(),OK
STL-1,4.500,0.000,ohm,(5-6-35-36=99.999),NG
D1-1,9.0,6.0,V,(2-5=12.6),NG
D1-2,10.5,7.5,V,(5-2=12.6),NG
...
end
```

解析要求：
1. 用 UART1 中断收字节，主循环按完整行解析，不要在中断服务函数里做字符串拆分、JSON 拼接或阻塞发送。
2. 普通数据行形式 `项目,上限,下限,单位,(测点=实测值),OK/NG`。**不能用简单逗号分割整行**，因为 `Open` 括号内部有多个逗号；需要按顶层逗号拆分或识别第一个 `(` 与配对 `)`，且校验字段边界。
3. 对 `Short,...,(),OK` 等无测量值行，不凭空生成实测值。
4. `Open` 可能有几十个测点，不能假设测点只有一个。不要根据单条 `Open` 的长行构造无限制的栈数组；应定义上限并检测溢出，内存不足时明确报错。
5. 文件中的 `test` 和 `end` 可作为**本批原始样本的标记**，但是 PDF/Excel 没有明确正式串口时序是否必然发送 `end`。实现为独立 `test_end_detector`，默认适配该样本的 `end` 行；必须在待确认事项声明该假设，不得将其称为 PDF 明确规定。
6. 每个测试项目都要有确定的映射处理。若 OPEN 多测点、多个同名项目、重复字段产生冲突，不能静默覆盖；先产出策略清单和测试覆盖，无法由资料确定的编码规则标记待确认。

## 5. 状态机及超时

建议状态枚举：`IDLE`、`WAIT_FIRST_DATA`、`COLLECTING`、`BUILD_RESULT`、`TX_RESULT`、`ERROR`。

```text
IDLE
  收到 RD_NUM → 检测模号 → UART2 回复 Result=模号或 ERR → IDLE
  收到 START,x → 校验模号
     失败 → UART2 回复 ERR → IDLE
     成功 → UART1 发送 testx\r\n → WAIT_FIRST_DATA，启动3秒计时
WAIT_FIRST_DATA
  3秒内无有效测试数据 → UART2 回复 {"Result":"ERR"}\r\n → 清理本次上下文 → IDLE
  收到有效测试数据 → COLLECTING
COLLECTING
  持续解析并累积项目结果，直到确认测试完成
  测试完成 → BUILD_RESULT → TX_RESULT → IDLE
```

- **3 秒无响应**：Excel 明确要求，不得随意改为 5 秒/10 秒；从成功下发 `testx\r\n` 时起计。
- **测试过程中的帧间超时及总超时**：附件并未给出确定数值。可提供可配置保护参数，但默认值不能被描述为协议要求。测试未完成不可返回 `OK`。
- **总结果判断**：当所有已确认测试项均为 OK，整体才为 OK；存在 NG 则整体为 NG。解析错误、缺帧和超时不能变成 OK；协议未定义这些异常的精细错误码，因此外部使用已明确的 `{"Result":"ERR"}`，并将原因留在内部状态。
- **一问一答**：不能边接收边向上位机连续上报半成品 JSON；不得对同一个有效 START 发送启动 ACK + 最终结果两帧。并发 START 行为资料未写明；为保证单一请求/单一响应，先限定一次一轮测试并单独说明忙状态处理。

## 11. 数据新格式 TXT：全部项目 JSON 映射与 Codex 实施约束（V1.1 新增）

### 11.1 依据、边界和资料优先级

1. PDF 第 2 页规定启动测试的回复结构：`{"MH":"x","Result":"OK/NG","测试项目":"测试数据:测试结果",...}`。无测试数据时可不写测试数据部分；PDF 的 OPEN 示例为 `"OPEN":":OK"` 或 `"OPEN":"1-2:NG"`。
2. Excel `Sheet1!B19` 明确给出 **普通项目映射锚点**：`D1-1,...,NG` → `{"MH":"1","Result":"NG","D1-1":"NG"}`，并注明“其余，以此类推”。本节将相同的“项目名:状态”映射应用到 STL、D、U 系列。
3. TXT 的 `test` 与 `end` 不当作测试项目字段。其余 **28 条项目行**顺序完整列于下表，其中 1 条 Open 含 **36 个测点**，1 条 Short 无测点数据，2 条 STL，16 条 D 系列，8 条 U 系列。
4. PDF **没有规定** Open 多测点时多个测点的合并分隔符；Excel **没有规定** Short 字段大小写。因此表中的这些项只作为 **待确认的候选编码**。不得将它们声称为 PDF 原文、不得自行静默丢弃测点。

### 11.2 从 TXT 到 828C JSON 的逐项映射表

### 11.5 结果值与标点：硬性实现规则

- JSON 整帧只含一个 `MH`、一个 `Result`，后续每一个源测试项一个独立的 JSON 键；不得生成重复键覆盖已有字段。
- `Result` 的值只能根据**本轮有效的全部测试项目**汇总为 `OK` 或 `NG`；存在一个 NG 则整体 NG；解析错误、缺失结束条件或超时不可报告 OK。
- 典型 `D1-1` 之类的普通项目仅上传 `"D1-1":"NG"`，不输出 `DATA,...`，不附加限值、电压、探针点，不依赖源文件的数值重新判定 NG。
- `STL-1`、`D1-1`、`U1-1-10` 中连接号 `-` 是测试项目名内容，必须保留；不改为下划线。
- `MH` 一律使用实测/绑定模号字符串（`"1"` 到 `"4"`），不复制测试项目上的额外字段或赋值来源不明的字符串。
- JSON 流中不能有 `test`、`end`、人类可读日志、`OPEN` 中未证实的新键、`steps`、`data` 等新增顶层字段。
- 每轮 START 成功时，只在完整测试结束后返回 **一个完整 JSON 对象 + `\r\n`**；测试主板原始多行转 JSON 单帧，不能每行发一个响应。
- `test` / `end` 是否真实通过串口输出仍是待确认项；测试模拟器按 TXT 顺序播放可复现样本。
