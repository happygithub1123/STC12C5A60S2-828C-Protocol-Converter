# 固件代码注释与代码风格规范

本规范根据当前 `STC12C5A60S2-828C-Protocol-Converter` 固件源码整理，用于后续维护、评审和新增模块。文档描述当前已经采用的代码组织方式，不要求回改历史源码。

## 1. 代码分层

```text
User/
  main.c                         程序入口、初始化和主循环
App/
  app_comm.c/.h                  828C协议、会话和JSON转换
Hardware/
  input_control.c/.h             X1～X5 GPIO配置、读取和模号识别
System/
  System.c/.h                    时钟、Timer0毫秒时基和中断优先级
  Uart1.c/.h                     主板串口驱动和接收/发送缓冲
  Uart2.c/.h                     上位机串口驱动和接收/发送缓冲
Public/
  Public_cfg.h                   公共类型、存储区宏和MCU头文件入口
  board_config.h                 时钟、容量、引脚相关配置
  STC12C5A60S2.h                 原厂MCU寄存器定义
```

模块职责保持单向清晰：

- `User` 只负责系统启动和调用主循环。
- `App` 负责协议命令、启动会话、主板记录校验、JSON流式输出和异常恢复。
- `Hardware` 只负责输入引脚配置、端口快照和唯一模号识别。
- `System` 负责串口寄存器、环形缓冲、串口中断、Timer0和毫秒计时。
- `Public` 提供所有模块共享的类型、配置和芯片寄存器定义。

串口中断只负责搬运字节和更新缓冲状态，协议解析必须在主循环中完成。固件不使用动态内存，不保存整轮测试结果，也不建立完整JSON副本。

## 2. 运行数据流

```text
UART2接收上位机命令
        ↓
App解析 START / RD_NUM / OK
        ↓
Hardware读取X1～X5并确认模号
        ↓
UART1发送 test\r\n
        ↓
主板UART1返回完整测试记录
        ↓
App校验记录并流式生成JSON
        ↓
UART2发送给上位机
```

`User/main.c` 的初始化顺序为：

1. `Sys_Init()`：初始化时钟、UART1、UART2、Timer0和中断优先级。
2. `InputControl_Init()`：配置X1～X5为准双向输入并释放端口。
3. `AppComm_Init()`：清理应用状态、会话状态和接收缓冲。
4. 打开总中断，循环调用 `AppComm_Poll()`。

## 3. 文件内部分区

自有 `.c` 文件按“内部定义”和“对外函数”分区。内部静态对象、宏和函数放在前面，对外函数放在后面。

```c
/*==============================================================================
 内部定义
 *============================================================================*/
```

```c
/*==============================================================================
 对外函数
 *============================================================================*/
```

如果文件没有内部实现，也可以只保留实际需要的分区。不要为了形式增加空分区。

## 4. 函数注释

对外函数和有边界条件、寄存器副作用或协议含义的内部函数，使用中文 Doxygen 风格注释：

```c
/**
 * @brief  初始化X1～X5输入，保留同端口其他引脚配置
 * @param  无
 * @retval 无
 */
void InputControl_Init(void)
{
    /* 函数实现 */
}
```

填写规则：

- `@brief`：说明函数完成的动作，使用动词开头，避免重复函数名。
- `@param`：说明参数用途、取值范围和调用前提；无参数写“无”。
- `@retval`：说明返回值含义和错误/无效情况；无返回值写“无”。
- 多个参数每个单独写一行，名称与函数声明保持一致。
- 对寄存器初始化、环形缓冲和协议状态等关键边界，应在注释中说明原因，而不是只重复代码字面含义。

头文件中的简短接口说明可以使用行尾注释：

```c
uint16 Sys_Millis(void); /* 原子读取16位毫秒计数。 */
```

接口说明不替代实现中的完整函数头；实现文件仍应保留必要的 `@brief / @param / @retval`。

## 5. 内部实现注释

内部注释使用简短中文 `//`，只解释以下内容：

- 硬件寄存器位的用途和引脚选择；
- 协议状态转换和优先级；
- 环形缓冲、临界区和中断保护原因；
- 长度、回绕、溢出和编码边界；
- 看起来不直观但必须保留的兼容行为。

推荐：

```c
ES = 0; // 读取16位索引快照，避免UART1中断同时修改。
```

避免：

```c
ES = 0; // 给ES赋值0。
```

注释必须描述“为什么”，代码已经清楚表达的“做什么”不重复解释。过长说明移到函数头或模块文档中。

## 6. 格式与排版

当前 `.clang-format` 的核心约定如下：

- 缩进四个空格，禁止Tab；
- 使用Allman花括号，函数、条件和循环的左花括号单独换行；
- 不设置强制行宽，寄存器初始化和对齐赋值可保持可读性；
- 短函数、短 `if` 和短循环不压缩到同一行；
- `case` 标签按当前工程规则缩进；
- 保持包含顺序和寄存器宏原样，不自动排序原厂相关头文件；
- 连续宏和连续赋值按现有配置对齐。

示例：

```c
if (next == UART1_RX_CAPACITY)
{
    next = 0u;
}
```

数字常量按用途添加后缀，例如 `0u`、`0x80u`；寄存器位操作应明确使用无符号常量，避免C51类型提升造成歧义。

## 7. 命名规则

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 对外函数 | 模块前缀 + PascalCase | `AppComm_Poll()` |
| 静态内部函数 | 模块前缀 + PascalCase | `AppComm_IsNumber()` |
| 文件内静态状态 | `g_` 前缀 | `g_milliseconds` |
| 宏和配置常量 | 全大写下划线 | `UART1_RX_CAPACITY` |
| 公共整数类型 | 固定工程类型 | `uint8`、`uint16` |
| 存储区标记 | 工程统一宏 | `XDATA`、`IDATA`、`CODE` |
| 状态常量 | 模块前缀 + 全大写 | `APP_RECEIVING` |
| 中断函数 | 使用芯片/编译器要求的入口形式 | `Uart1_Isr()` |

变量名应表达用途，避免单字母变量跨越较大代码范围。循环中的短变量可以使用 `i`、`at`、`pos` 等，但必须保持作用域短且含义明确。

## 8. 接口和依赖约束

- `User` 可以调用各层初始化和轮询接口，不在其中实现协议细节。
- `App` 可以调用 `Hardware` 的输入接口和 `System` 的串口/计时接口。
- `Hardware` 不解析协议，不直接生成JSON。
- `System` 不判断 `START`、`RD_NUM` 或主板记录内容。
- `Public` 不包含业务状态，不依赖 `App`、`Hardware` 或 `System`。
- UART ISR 不调用协议解析、字符串处理或JSON编码函数。
- 新增容量、引脚或时钟参数优先放入 `Public/board_config.h`，不要散落在业务文件中。
- 原厂 `Public/STC12C5A60S2.h` 保持原样，不进行格式化、重命名或中文编码修复。

## 9. 修改和验证要求

修改代码时按以下顺序检查：

1. 先确认改动属于 `App`、`Hardware`、`System` 或 `Public` 哪一层。
2. 新增函数时同时添加中文 `@brief / @param / @retval` 注释。
3. 新增协议或容量常量时集中放入配置头文件。
4. 检查中断与主循环之间的共享变量是否需要 `volatile` 或临界区保护。
5. 运行格式检查或人工检查四空格、独立花括号和分区顺序。
6. 使用 Keil/EIDE 构建，确认没有新增警告；协议修改还需执行对应串口样例和边界测试。

构建和输出目录中的 `Objects`、`Listings`、HEX、OBJ、日志以及个人IDE状态不属于源代码规范内容，不应提交到版本库。

## 10. 维护原则

- 先维护模块边界，再扩展函数；不要把硬件寄存器操作散落到App。
- 先保持协议输入校验完整，再优化发送速度；不得静默截断数据。
- 解释特殊行为的原因，避免只留下无法验证的经验性注释。
- 修改当前约定时，同时更新本文件和根目录 README，保证源码与文档一致。
